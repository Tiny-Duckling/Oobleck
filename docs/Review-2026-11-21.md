## Resolved findings

### 1. Docker build broken by the package rename — fixed

`backend/Cargo.toml` produces the binary `oobleck-backend`, but the Docker setup previously referenced `quiz-backend`.

Now updated:

- `backend/Dockerfile` copies `target/release/oobleck-backend`
- `backend/docker-entrypoint.sh` execs `oobleck-backend`
- `docker-compose.yml` uses `RUST_LOG: oobleck_backend=debug,...`
- `README.md` uses `cargo clean -p oobleck-backend`
- `backend/src/main.rs` default log filter uses `oobleck_backend=debug`
- `backend/tests/config.rs` doc comment uses `oobleck_backend`

The only remaining references are in the gitignored `backend/.idea/workspace.xml`.

**Note:** The fix was verified statically (`cargo metadata` lists `oobleck-backend`), not with a full `docker compose build`.

### 2. Concurrent double-submit corrupted `attempt_answers` — fixed

Previously the attempt was resolved outside the transaction, the update did not guard on `submitted_at IS NULL`, and two parallel submits could both return `200` and insert duplicate answer rows.

Current implementation in `backend/src/routes/quizzes.rs`:

- Resolves and locks the attempt inside the transaction with `FOR UPDATE`.
- Returns `404` for a missing/foreign attempt.
- Returns `409 Conflict` when the attempt was already submitted.
- Guards the update with `WHERE id = $1 AND submitted_at IS NULL` and checks `rows_affected()`.
- Loads one correct option per question via `JOIN LATERAL ... LIMIT 1`.

New migration `backend/migrations/0006_unique_attempt_answers.sql`:

- Deletes pre-existing duplicate `(attempt_id, question_id)` rows.
- Adds a unique index on `attempt_answers (attempt_id, question_id)`.

**Verification:** 10 parallel rounds of two simultaneous submits produced exactly one `200` and one `409` per round, with 4 answer rows per 4-question attempt. A single race produced:

```text
code1=200
code2=409 {"error":"attempt already submitted"}
answer rows=4
```

Normal flow also still works: start → reuse the same in-progress attempt → submit → history shows the score → resubmit returns `409` → starting again creates a new attempt.

**Migration note:** `0005` and `0006` were applied to the local dev DB during verification. Do not edit them afterwards without resetting/repairing the SQLx migration checksum.

## Outstanding findings

### High priority

#### 1. In-progress attempts need a lifecycle/UX decision

Every quiz page load calls `startQuizAttempt` (`frontend/src/routes/quiz/[id]/+page.svelte`), which creates a DB row even if the user only looks at the quiz. Consequences:

- Opening all seeded quizzes creates a permanent “In progress” history row for each.
- The history page links quiz titles to `/quiz/{id}` even for completed attempts, so viewing a past quiz creates another in-progress row.
- Generated quizzes add more rows; there is no TTL, cleanup, or discard path.
- “In progress” implies saved answers, but no answers are stored until submit. The attempt detail page says “This attempt has no answers recorded.”

Options:

- Create the attempt only on the first answer/submit.
- Add a “Discard attempt” action and a periodic cleanup job.
- Persist partial answers if “In progress” should be literal.
- At minimum, relabel it to “Started” and add a resume link on the attempt detail page.

#### 2. SPA param-change bug still present

`frontend/src/routes/quiz/[id]/+page.svelte` and `frontend/src/routes/attempts/[id]/+page.svelte` fetch in `onMount` while deriving the id from `page.params.id`. SvelteKit reuses the component when only `[id]` changes, so navigating `/quiz/A` → `/quiz/B` leaves A’s quiz, selections, and `attemptId` in place.

Fix with an `$effect` keyed on the id, `afterNavigate`, or `{#key id}`.

#### 3. Grading integrity gaps

- `submit_quiz` does not verify that `selected_option_id` belongs to `question_id`. A client can send an option from another question; the FK passes and the review shows the wrong text.
- There is no DB guarantee of exactly one correct option per question. The submit query now picks one deterministically, but a partial unique index on `options (question_id) WHERE is_correct` would enforce the invariant.

### Medium priority

- **`start_attempt` can leave stuck attempts.** It only checks that the quiz exists. A quiz with no questions creates an attempt that can never be submitted. A quiz deleted between the existence check and the insert produces an FK violation → 500.
- **API docs are stale.** `README.md` does not document `POST /api/quizzes/:id/attempt`, the optional `attempt_id` in the submit body, nullable attempt fields, or the new `409` response. `docs/Review.md`, `plan.md`, and `frontend/README.md` are also stale.
- **No attempt-lifecycle tests.** The concurrency fix and start/reuse/submit flow are only covered by manual verification. Add integration tests for start/reuse, submit, resubmit (`409`), history, and concurrent submits.
- **Formatting and lint debt.** `cargo fmt --check` still reports diffs; Clippy’s 11 warnings are pre-existing (`seed_gre.rs` borrows, one `auth.rs` warning).
- **History query scalability.** `ORDER BY COALESCE(submitted_at, started_at) DESC` cannot use an index, and history has no pagination. Fine at current scale, but in-progress rows make it grow faster.
- **`started_at` on resume.** Reusing an old in-progress attempt keeps the original `started_at`, so history shows the first-open date rather than the latest resume. Consider updating it or adding `last_opened_at`.

### Low priority / pre-existing

- No rate limiting on auth, attempt-start, or quiz-generation endpoints.
- Generated quizzes are never cleaned up.
- `attempt_answers` FKs lack delete behavior (`question_id`, `selected_option_id`).
- `seed_gre` still iterates a `HashMap`, so `--reset` is not deterministic despite the comment.
- `make_cloze` uses byte offsets from `to_lowercase()` against the original string; non-ASCII input could panic or slice incorrectly.
- `AppError::Internal` would leak its message if ever constructed with details; currently only generic messages are used.
- Docker hardening: backend runs as root, no backend healthcheck, frontend `depends_on` backend without a health condition.
- Frontend polish: attempt detail page has no resume link; history uses `score === null` for in-progress but `submitted_at === null` for the Resume link; `startQuizAttempt` failures are silently swallowed.
- `backend/.idea/workspace.xml` still references the old `quiz-backend` name (gitignored).
- A11y, nginx security headers, and PDF line-height edge cases noted in the previous review remain unaddressed.

## Strengths

- Server-side grading; the quiz-fetch endpoint never selects `is_correct`.
- Argon2 password hashing, JWT expiry, generic login error.
- Attempt ownership checks and 404-for-foreign-attempts behavior.
- Typed API client and shared `AttemptReview` component.
- Migration `0005` correctly backfills `started_at` and enforces one in-progress attempt per user/quiz.
- The new submit path correctly serializes concurrent submissions and protects `attempt_answers` with a unique index.
- Idempotent seeding; embedded GRE word data.
- Svelte 5 runes, strict TypeScript, clean `svelte-check`.
- Docker Compose with a health-checked database, same-origin nginx proxy, and required secrets.
